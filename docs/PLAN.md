## 1. 목표와 진행 원칙

핵심 메시지는 **Every Excuse Deserves an Exhibition. / 모든 핑계에는 전시될 자격이 있다.**입니다. React·Tailwind CSS·FastAPI·SQLite 기반을 유지하고, 텍스트 핵심을 먼저 완성한 뒤 사진전을 포함한 MVP, 이후 AI 회화전 확장으로 진행합니다.

기존 1~2주 목표는 텍스트 기본 MVP의 초기 가정이며 히어로·사진·AI 추가 일정까지 보장하지 않습니다. 사진·AI 개발 일정은 세부 정책과 매체 처리 방식을 정한 뒤 다시 추정합니다.

**진행 순서는 Phase 1 검증·Git 저장 → Phase 1.5 설치미술 히어로 → Phase 2~7 기본 등록·DB·핵심 기능 → Phase 8 사진 포함 MVP → Phase 9 AI 확장입니다.** Phase 0은 완료 상태를 보존합니다. 기존 Phase 2~7의 번호와 의존성을 유지하고 새 단계를 삽입·추가합니다.

현재 단계의 검증·완료 판단·Git 저장을 끝낸 뒤 다음 단계로 갑니다. 여러 Phase를 동시에 개발하지 않습니다. **이번 요청은 네 기획 문서 수정만 수행하며 코드·PROGRESS 수정, 패키지 설치, 커밋·푸시를 실행하지 않습니다.** 아래 Git 절차는 향후 각 단계 저장 시 적용할 계획입니다.

위 표는 확장 기획 검토 당시의 스냅샷입니다. 이후 Phase 1 검증·Git 저장 상태와 수행한 검사·보류 항목은 [PROGRESS.md](./PROGRESS.md)에서 관리합니다. 기존 Phase 1 작업에서 브라우저 자동화가 중단되어 필수 화면 검증을 끝내지 못했으며 실제 브라우저 미검증 항목을 통과로 기록하지 않습니다. 샘플 필터·인기순은 실제 DB 기반 F04·F07 완료가 아닙니다.

- 기존 기능과 운영 정책은 MVP·PRD·SPEC을 따릅니다. 새로운 정책을 기본값처럼 추가하지 않습니다.
- 미정 사항은 **확인 필요**로 유지하고, 그 결정이 필요한 작업을 완료로 기록하지 않습니다.
- 각 단계에서 기본적인 빈 결과·오류 안내를 함께 만듭니다. 모든 오류 처리를 마지막 단계로 미루지 않습니다.
- 임시 화면이나 예시 데이터는 개발 확인용입니다. DB에 저장된 실제 결과처럼 표시하거나 해당 기능을 완료한 것으로 판단하지 않습니다.
- 프론트엔드는 사용자 화면, 백엔드는 요청을 처리하는 서버, DB는 작품과 투표를 저장하는 공간입니다. API는 화면과 서버가 데이터를 주고받는 약속입니다.

## 3. 모든 Phase에 적용할 Git 저장 절차

현재 로컬 저장소는 `master` 브랜치이며 `origin/master`를 추적합니다. 등록된 GitHub 원격 주소는 `https://github.com/0214jw/EXCUSE-ME.git`입니다. 원격 등록 상태를 확인한 것이며, 이번 문서 작성에서 GitHub 접속이나 푸시 성공까지 확인한 것은 아닙니다.

각 Phase의 테스트와 완료 기준을 확인한 뒤 다음 순서로 저장합니다.

1. `git status`와 `git diff`로 이번 단계의 변경 파일과 내용을 확인합니다.
2. 실제 비밀번호·API 키·`.env`·DB 파일·업로드 파일이 없는지 확인합니다. `.venv`, `node_modules`, 캐시, 빌드 결과, 로그도 커밋하지 않습니다. `.env.example`에는 실제 비밀값을 넣지 않습니다.
3. 이번 단계에서 바꾼 파일만 경로를 지정해 `git add`합니다. 다른 작업의 파일까지 일괄로 추가하지 않습니다.
4. `git diff --cached`로 실제 커밋될 내용을 다시 확인한 뒤 아래 단계별 예시 메시지로 커밋합니다.
5. 현재 브랜치와 원격을 다시 확인하고 GitHub에 `git push`합니다. 현재 추적 관계가 유지된다면 인자 없는 `git push`를 사용할 수 있습니다.
6. 커밋 번호·테스트 결과·푸시 결과를 기록하고 작업 상태를 확인한 뒤 다음 Phase로 넘어갑니다.

원격 연결·로그인·네트워크 문제로 푸시에 실패하면 로컬 커밋을 보존하고 '로컬 저장 완료, GitHub 저장 미완료'로 구분합니다. 원인을 해결해 푸시를 확인한 뒤 다음 단계로 진행합니다. 원격이 사라졌다면 연결할 저장소를 확인하며, 임의의 다른 저장소 생성이나 강제 푸시로 해결하지 않습니다.

아래 커밋 메시지는 향후 실행할 예시이며 이번 PLAN 작성의 커밋 지시가 아닙니다. Phase별 Git 절차는 이 절을 공통으로 적용합니다.

### 7. 완료 판단 기준

## Phase 2: 작품 등록과 SQLite DB 연결

### 1. 개발 목표

방문객이 기증한 텍스트 작품이 SQLite에 저장되고, 새로고침 후에도 감상할 수 있게 합니다.

### 2. 구현 기능과 요구사항 연결

- F02: 입력 검증, 방문객 연결, 작품 저장, 등록 성공 후 감상실 이동.
- F03: 등록 결과 확인에 필요한 기본 목록·상세 조회를 이 단계에 포함합니다.
- F01: 기증 버튼을 실제 등록 기능으로 연결합니다.
- F10: 작가명 입력·저장·표시만 적용합니다. 이미지 방식 선택은 Phase 8·9에서 연결합니다.
- 공통: 브라우저별 데모 ID 생성·유지와 한계 안내를 적용합니다.

### 3. 프론트엔드 작업

- 작품명·핑계 내용·카테고리 한 가지·작가명 입력을 연결합니다. 작가명 필수 여부·검증 기준을 먼저 확정합니다. 사진·AI 선택은 아직 실제 기능으로 연결하지 않습니다.
- 빈 값·공백뿐인 제목이나 내용·잘못된 카테고리의 오류를 표시합니다.
- 확정된 방식으로 ID를 만들고 유지하며 요청에 전달합니다. 실제 인증으로 소개하지 않습니다.
- 등록 성공 시 새 작품 감상실로 이동하고 목록에서 확인할 수 있게 합니다.
- 저장 중·실패·응답을 받지 못한 상황을 성공과 구분합니다. 실패 시 다시 시도할 수 있게 합니다.

### 4. 백엔드 작업

- 등록과 기본 목록·상세 조회를 처리합니다.
- 제목·내용·카테고리와 확정된 작가명 기준을 검증하고 현재 방문객 ID를 작품에 연결합니다. 표시 작가명으로 권한을 판단하지 않습니다.
- 작품 번호와 등록 시각을 자동 기록합니다.
- 잘못된 입력과 서버·DB 오류를 구분해 화면에 전달합니다. 응답 형식은 확인 후 결정합니다.

### 5. DB 관련 작업

- 작품 저장 구조와 최초 생성 방법을 구성합니다. 필요한 정보는 제목·내용·카테고리·작가명·작품 번호·등록 시각·방문객 ID입니다. 기존 데이터가 있다면 작가명 표시·변환 정책을 확인하고 보존합니다.
- 서버를 다시 실행해도 저장된 작품을 조회할 수 있게 합니다.
- DB 구조를 재현하는 설명이나 생성 자료를 관리하되 실제 `.db`·`.sqlite`·`.sqlite3` 파일은 커밋하지 않습니다.
- 투표 저장과 연결 처리는 Phase 4에서 완성합니다. ID 구분을 회원가입용 사용자 계정으로 확장하지 않습니다.

### 6. 직접 확인할 테스트

- SPEC F02-T01~T04와 F10-T01을 확인합니다. A의 기증 작품·작가명을 새로고침과 다른 ID의 B에서 조회하고 작가명과 방문객 ID가 별개로 저장되는지 확인합니다. 실제 수정·삭제 권한 검증은 Phase 3의 F10-T05에서 수행합니다.
- 제목·내용을 각각 빈 값·공백뿐인 값으로 바꾸고, 카테고리 미선택·잘못된 값도 확인합니다.
- 서버 재실행 후 작품 유지, 서버 중단·DB 오류·응답 유실 시 안내와 실제 저장 결과를 확인합니다.
- 글자 수 정책 확정 후 F02-T05와 SPEC E02의 상한 직전·동일·초과 테스트를 실행합니다. 미정이면 보류로 기록합니다.

### 7. 완료 판단 기준

- 기증 → 실제 저장 → 감상실 → 목록 확인이 연결되고 결과가 유지됩니다.
- 잘못된 입력은 저장되지 않고 이유가 보입니다.
- ID의 재방문 유지와 브라우저별 구분이 동작하고 한계 안내가 있습니다.
- 이 단계 완료에 직접 필요한 정책이 결정되고 관련 테스트를 통과해야 합니다. 보류 항목을 통과로 바꾸지 않습니다.
- 커밋·푸시를 완료합니다. 예시 메시지: `feat: 작품 기증과 SQLite 저장 연결`.

### 8. 다음 Phase 진입 조건

등록·기본 조회·ID 유지·실패 처리 확인과 Git 저장이 끝나야 합니다. 저장되지 않는 문제나 입력 기준의 미정 상태를 남겨 둔 채 수정·삭제로 넘어가지 않습니다.

## Phase 3: 작품 목록, 상세 조회, 수정 및 삭제

### 1. 개발 목표

작품을 안정적으로 감상하고, 기증자가 본인 작품을 고치거나 삭제할 수 있게 합니다.

### 2. 구현 기능과 요구사항 연결

- F03: 최신 등록순 목록·전체 상세 정보·빈 목록·없는 작품 처리 완성.
- F05: 화면과 서버의 ID 비교, 수정 검증, 삭제 확인·취소·실행.
- F02: 등록과 수정에 같은 입력 기준 적용.
- 투표를 유지하거나 함께 삭제하는 F05의 연결 기준은 Phase 4에서 표가 생긴 뒤 추가 확인합니다.

### 3. 프론트엔드 작업

- 목록에 제목·작가명·카테고리·명작 인정 수를, 감상실에 번호·제목·작가명·전체 내용·카테고리·등록 시각·투표 수를 표시합니다. 작가명 수정 허용 여부는 확인 필요이며 기존 수정 항목을 임의로 확대하지 않습니다.
- 본인 작품에서만 수정·삭제 버튼을 표시합니다.
- 제목·내용·카테고리를 수정하고 저장 결과를 표시합니다.
- 삭제 확인과 취소를 구현하고, 확정 성공 시 삭제한 작품을 계속 감상 가능한 것처럼 보여주지 않습니다.
- 빈 목록의 기증 버튼, 없는 작품의 전시관 복귀 버튼, 조회·수정·삭제 오류 안내를 연결합니다.

### 4. 백엔드 작업

- 목록을 최근 등록순으로 조회하고 상세 필수 정보를 반환합니다.
- 수정·삭제 요청에서 작품의 ID와 현재 방문객 ID를 비교해 불일치를 거절합니다. 버튼을 숨기는 것만으로 끝내지 않습니다.
- 수정에 등록과 같은 검증을 적용합니다.
- 없는 작품과 권한 없는 요청, 서버·DB 실패를 구분합니다.
- 삭제 후 작품이 조회 대상에서 제외되도록 처리합니다. 삭제 복구 기능은 만들지 않습니다.

### 5. DB 관련 작업

- 작품 조회·수정·삭제를 연결하고 성공 결과를 다시 조회해 확인합니다.
- 수정이 작품의 소유자를 임의로 바꾸는 기능이 되지 않도록 기존 작품과 방문객 연결을 유지합니다.
- 아직 표가 없는 상태의 투표 수를 실제 남아 있는 표 수에 맞게 표시합니다. 임의의 인기 수치를 저장하지 않습니다.
- 투표 생성 이후 수정 시 표 보존·삭제 시 연결 표 제거를 확인할 항목을 Phase 4에 남깁니다.

### 6. 직접 확인할 테스트

- SPEC F03-T01~T06과 F05-T01~T06 중 현재 가능한 항목을 수행합니다. 실제 표가 있는 F05의 연계 검증은 Phase 4에 명시해 이어갑니다.
- A의 작품을 B로 조회하고, B의 ID로 서버에 직접 수정·삭제를 요청해 거절되는지 확인합니다. F10-T05에서 같은 작가명을 쓰더라도 권한이 생기지 않는지 확인합니다.
- 빈 입력 수정, 삭제 취소·확정, 새로고침, 없는 주소, 감상실을 연 뒤 다른 창에서 삭제된 작품을 확인합니다.
- 서버·DB 오류 시 성공으로 표시하지 않는지 확인합니다. 응답 유실 때는 실제 변경 결과를 별도 조회합니다.

### 7. 완료 판단 기준

- 현재 작품의 목록·상세·본인 수정·삭제와 관련 예외가 동작합니다.
- 다른 ID의 요청은 화면과 서버에서 제한되며 거절 후 작품은 유지됩니다. 실제 인증이 아니라는 한계를 유지합니다.
- 빈 목록과 없는 작품의 안내·복귀가 동작합니다.
- 투표 연계처럼 후속 단계에서 확인할 항목을 전체 기능 완료로 표시하지 않습니다.
- 커밋·푸시를 완료합니다. 예시 메시지: `feat: 작품 조회와 본인 작품 관리 구현`.

### 8. 다음 Phase 진입 조건

조회·소유자 비교·수정·삭제의 기본 흐름과 실패 처리가 동작하고 Git 저장이 끝나야 합니다. Phase 4에서 결정할 투표 정책과 이어서 검증할 F05 항목을 확인한 뒤 진행합니다.

## Phase 4: 공감 투표, 카테고리 필터, 인기순 정렬, 명예의 전당

### 1. 개발 목표

명작 인정·취소와 카테고리 탐색을 제공하고, 투표 수 기반 TOP 10을 보여줍니다.

### 2. 구현 기능과 요구사항 연결

- F04: 전체·카테고리별 필터와 선택 상태·빈 결과.
- F06: 방문객별 한 표·취소·중복 방지·상태 유지.
- F07: 인기순 계산과 TOP 10, 동점 규칙.
- F03·F05: 투표 수 표시, 수정 시 표 유지, 삭제 시 연결 투표 제거 재확인.
- F01: 명예의 전당 버튼의 실제 목적지 연결.
- 전시관의 최신순은 유지합니다. 전시관에 인기순 전환 옵션을 새로 넣지 않습니다.

### 3. 프론트엔드 작업

- 감상실의 명작 인정 버튼에 본인 상태와 수를 표시하고 다시 누르면 취소하도록 연결합니다.
- 전체·지각·과제·약속·운동·기타 필터와 현재 선택 표시를 구현합니다.
- 명예의 전당에서 순위·투표 수를 표시하고 감상실로 연결합니다.
- 빈 결과와 요청 실패, 빠른 클릭 중 상태 표시를 다룹니다. 세부 클릭 처리 방식은 확인된 설계를 따릅니다.

### 4. 백엔드 작업

- 방문객 ID와 작품 조합으로 투표를 관리하고 취소는 본인 표에만 적용합니다.
- 중복 인정과 반복 취소, 빠른 요청에서도 중복 표·음수 투표 수가 생기지 않게 합니다.
- 카테고리 필터 결과는 최근 등록순으로 반환합니다.
- 명예의 전당은 투표 수 내림차순 → 등록 시각 내림차순 → 작품 번호 내림차순으로 최대 10개를 조회합니다.
- 투표·취소·삭제 후 재조회에 현재 결과를 반영합니다. 실시간 자동 갱신은 요구하지 않습니다.

### 5. DB 관련 작업

- 작품과 방문객 ID에 연결된 투표 저장 구조와 기존 DB에 반영할 방법을 구성합니다.
- 같은 ID와 작품에 최대 한 표만 유지할 수 있도록 저장 일관성을 지키는 방법을 적용합니다. 구체적인 DB 제약·저장 방식은 구현 전에 결정합니다.
- 작품의 투표 수가 실제 남은 표 수와 일치하는지 확인합니다.
- 수정 시 표가 유지되고 삭제 시 연결된 표까지 제거되도록 Phase 3의 처리를 완성합니다.
- 일부 저장 처리 실패를 성공으로 끝내지 않는 방법을 정하고 검증합니다.

### 6. 직접 확인할 테스트

- SPEC F04-T01~T04, F06-T01~T06, F07-T01~T05를 수행합니다.
- A의 작품에 B·C가 인정하고 B만 취소해 C의 표가 유지되는지 확인합니다. 본인 작품 투표 정책은 별도 확정 후 확인합니다.
- 동일 인정 요청 중복 전달, 빠른 클릭, 반복 취소 후 ID별 최대 한 표·수의 일치·음수 방지를 확인합니다.
- 작품 0개·1개·10개 미만·11개 이상, 투표 수 동점, 등록 시각까지 같은 자료로 순위 규칙을 확인합니다.
- 표가 있는 작품 수정·삭제 후 목록·상세·필터·명예의 전당을 재조회해 F05의 남은 연계 기준을 검증합니다. 랜덤 제외는 Phase 5에서 확인합니다.
- 조회·저장 실패를 빈 결과·성공으로 표시하지 않는지 확인합니다.

### 7. 완료 판단 기준

- 필터·투표·취소·현재 투표 수·명예의 전당이 확정 기준대로 연결됩니다.
- 중복 표와 음수가 없고, 새로고침 후 방문객별 상태가 유지됩니다.
- 수정 시 표 유지와 삭제 시 연결 표 제거가 확인됩니다.
- 명예의 전당 추가 기간·최소 표 수·운영자 선정 조건을 넣지 않습니다.
- 직접 영향을 주는 미정 투표 정책을 해결하고 커밋·푸시를 완료합니다. 예시 메시지: `feat: 명작 인정과 필터 및 명예의 전당 구현`.

### 8. 다음 Phase 진입 조건

F04·F06·F07과 F05의 투표 연계 테스트를 마치고 Git 저장이 끝나야 합니다. 순위 오류나 중복 투표 문제가 남아 있으면 먼저 해결한 뒤 Phase 5로 진행합니다.

## Phase 5: 랜덤 작품 감상 및 UX 개선

### 1. 개발 목표

무작위 작품 발견 기능을 연결하고, 기증에서 감상·투표로 이어지는 이용 흐름을 다듬습니다. UX는 사용자가 기능을 이해하고 이용하는 경험을 뜻합니다.

### 2. 구현 기능과 요구사항 연결

- F08: 랜딩·감상실의 랜덤 감상, 작품 수별 동작.
- F01: 아직 남은 랜덤 버튼 동작 연결.
- F03·F05: 삭제 작품 접근과 랜덤 대상 제외 확인.
- F01~F08 공통: 기존 요구사항의 로딩·빈 결과·실패·복귀 안내를 점검합니다.

### 3. 프론트엔드 작업

- 랜딩페이지와 감상실의 랜덤 버튼을 실제 요청으로 연결합니다.
- 결과 작품 감상실로 이동하고, 작품이 없으면 안내와 기증 버튼을 표시합니다.
- 각 기능의 버튼 이름, 저장 중 표시, 빈 결과와 실패 안내, 전시관 복귀를 일관되게 정리합니다.
- 새로운 검색·추천·알림 기능을 UX 개선이라는 이유로 추가하지 않습니다.

### 4. 백엔드 작업

- 삭제되지 않은 전체 작품에서 무작위로 한 작품을 선택합니다.
- 한 작품이면 해당 작품을, 0개이면 작품이 없음을 화면에서 구분할 수 있게 처리합니다.
- 선택 후 삭제된 작품과 조회 실패를 처리합니다. 자동 재선택은 정책 확인 없이 추가하지 않습니다.

### 5. DB 관련 작업

- 현재 남아 있는 작품만 선택 대상으로 조회합니다.
- 개인 취향 정보나 랜덤 감상 기록 같은 새 저장 기능을 추가하지 않습니다.
- 삭제한 작품이 어떤 조회에서도 되살아나지 않는지 확인합니다.

### 6. 직접 확인할 테스트

- SPEC F08-T01~T05와 F01-T03을 수행합니다.
- 작품 0개·1개·여러 개, 삭제된 작품 제외, 선택 후 삭제, 서버·DB 조회 실패를 확인합니다.
- 여러 번 감상해 유효한 작품으로 이동하는지 보고 선택 로직도 확인합니다. 연속으로 같은 작품이 나왔다는 사실만으로 실패로 판단하지 않습니다.
- 랜딩 → 전시관 → 감상 → 인정 → 명예의 전당 → 랜덤 → 기증 흐름을 직접 따라갑니다.

### 7. 완료 판단 기준

- 랜딩·감상실에서 랜덤 감상이 동작하고, 0개·1개·삭제·실패 안내가 맞습니다.
- F01의 주요 목적지 버튼이 실제 기능에 연결되어 있습니다.
- F05의 삭제 작품 랜덤 제외까지 확인됩니다.
- 확정된 F01~F08 기능이 서로 연결되고 남은 작업이 디자인·최종 검증으로 구분됩니다.
- 커밋·푸시를 완료합니다. 예시 메시지: `feat: 랜덤 작품 감상과 이용 안내 개선`.

### 8. 다음 Phase 진입 조건

랜덤 감상과 전체 이동 흐름 테스트·Git 저장을 마칩니다. Phase 6에 사용할 Figma 원본과 적용 대상 화면을 확인한 뒤 디자인 반영을 시작합니다.

## Phase 6: Figma 디자인 반영 및 모바일 반응형 UI

### 1. 개발 목표

확인된 Figma 디자인을 기존 기능에 적용하고 휴대전화와 PC에서 사용할 수 있도록 화면을 다듬습니다. 반응형 UI는 화면 너비에 맞춰 배치가 조정되는 화면입니다.

### 2. 구현 기능과 요구사항 연결

- F01~F08·F09 및 F10 작가명 부분의 화면 표현과 사용성을 확인합니다. 사진·AI UI는 해당 후속 단계에서 별도 확인합니다.
- 기존 기능·버튼·입력 검증·권한·순위 정책은 유지합니다.
- Figma 원본, 화면 범위, 모바일 디자인은 **확인 필요**입니다. 없는 디자인을 반영 완료로 처리하지 않습니다.

### 3. 프론트엔드 작업

- 확정된 디자인의 색상·글꼴·간격·작품 표시·버튼 구성을 Tailwind CSS로 적용합니다.

## Phase 9: AI 이미지 생성·AI 회화전 (추가, 후속 확장)

### 1. 개발 목표

사용자가 작성한 핑계로 회화를 생성하고 결과를 확인한 뒤 작품으로 등록하게 합니다. 기존 핵심 서비스가 완성된 후 별도로 진행합니다.

### 2. 구현 기능과 요구사항 연결

F12를 구현하고 F10의 AI 선택·F13의 AI 혼합 감상을 확장합니다. 기존 F01~F08 정책과 사진 기능을 유지합니다.

### 3. 프론트엔드 작업

수채화·유화·점묘화·연필 드로잉·콜라주 선택, 생성 진행·실패·결과 확인·등록 선택·저장 결과를 구분합니다. 생성만으로 자동 등록하지 않으며 사진과 AI 방식을 동시에 쓰지 않습니다. 확정된 비용·제한 안내와 재생성·취소 정책을 적용합니다.

### 4. 백엔드 작업

확정된 제공사·모델과 서버에서 연동하고 비밀키를 클라이언트·Git에 노출하지 않습니다. 비용·요청 제한·중복·응답 유실·실패 처리를 결정된 정책으로 적용하며 불확실한 요청을 무조건 무료 재시도하지 않습니다. 핑계 문장 생성 기능을 추가하지 않습니다.

### 5. DB·미디어 관련 작업

미등록 생성 결과와 등록 작품을 구분하고 선택한 결과·스타일·출처를 기존 작품 정보에 연결합니다. 임시·미등록·실패·삭제 생성물의 보관·정리 정책을 적용하고 텍스트·사진 작품 및 기존 투표를 보존합니다. 정확한 API·스키마·진행 상태 저장 방식은 확인 필요입니다.

### 6. 직접 확인할 테스트

SPEC F12-T01~T05, F10의 AI 단계, F13의 텍스트/사진/AI 통합과 E10을 확인합니다. 다섯 스타일·미등록 결과·비용/제한 경계·생성 실패·재시도·중복·취소·저장 실패·비밀키 비노출을 검증하고 기존 핵심·사진 기능을 회귀 확인합니다.

### 7. 완료 판단 기준

다섯 스타일 생성·결과 확인·사용자 선택 등록·혼합 전시와 확정된 비용/운영/실패 정책이 통과하고 Git 저장이 끝나야 AI 확장 완료입니다. 사진 MVP 완료와 별도로 기록합니다.

### 8. 이후 조건

검증하지 못한 비용·제한·예외 항목은 보류로 남깁니다. 사용자에게 실제 제공할 범위와 남은 결함을 정리하고 새로운 기능을 임의로 더하지 않습니다.

## 4. 범위 유지와 다음 실행 단계

댓글·답글, AI 핑계 문장 생성, 정식 회원가입·로그인, 검색, 알림, 팔로우, 개인별 추천, 별도 관리자 화면, 삭제 작품·방문객 ID 복구는 계속 제외합니다. 사진은 Phase 8의 MVP에, AI 이미지 생성은 Phase 9의 확장에 한정합니다. 복잡한 실제 목록 정렬 옵션과 무한 스크롤은 후순위이며 샘플 인기순은 현재 코드에만 보존합니다.

데모 방문객 ID는 실제 보안 인증을 대신하지 못합니다. ID를 복사·변경한 사람이나 여러 ID로 투표하는 실제 한 사람을 구분할 수 없으며, 이를 정식 인증 수준의 보안으로 안내하지 않습니다.
