## Phase 1: 랜딩페이지와 상설 전시관 기본 UI

### 구현 상태

- `/`: 기존 EXCUSE ME! 랜딩페이지, 소개·전시 관람하기 링크·기증 준비 중 안내·대표 샘플 미리보기.

2. `POST /api/curator` 한 번이 원문·현재 제목·카테고리를 바탕으로 후보 3개와 한국어 해설 2~4문장을 함께 요청합니다. 브라우저에서 OpenAI를 직접 호출하지 않습니다. 방문객 ID·요청 ID·작가명은 OpenAI에 보내지 않습니다.
3. 제목 후보 선택은 작품명 입력란에 반영되며 직접 수정할 수 있습니다. 제목 변경만으로 재생성하지 않습니다. 다시 생성은 별도 버튼을 눌러야 합니다.
4. 별도 작품 설명 영역에서 생성 내용을 미리보기·수정합니다. 확인 체크를 선택한 설명만 `refined_description`과 `description_confirmed: true`로 기증 요청에 포함합니다. 확인하지 않으면 설명을 보내지 않고 기존 텍스트 작품으로 기증할 수 있습니다.
5. 원문·제목·카테고리 또는 설명 수정 시 확인 체크를 해제합니다. 생성 당시 원문/카테고리와 달라지면 오래된 추천 안내를 표시합니다. 요청 도중 원문을 수정해도 결과에 당시 입력을 연결해 경고할 수 있도록 했습니다.
6. 새 생성 실패 시 기존 추천·편집 중 설명·작품 입력은 유지합니다. 일반 텍스트 기증을 막지 않습니다. 생성 중에는 중복 요청과 기증 완료를 잠시 막고, 응답 후 사용자 확인을 거칩니다.
7. 상세 화면은 최종 제목과 별도 설명을 보여주고 `원문 핑계 확인하기`를 펼쳐 원문도 확인할 수 있습니다. 설명 없는 기존 작품은 기존 임시 설명으로 표시됩니다.

### 모델·호출·키·비용 제어

- 기본 모델: **`gpt-5.6-terra`**. 확인한 공식 문서에서 지능·비용 균형을 갖춘 기존 mini급 모델로 설명하고, Responses API·Structured Outputs를 지원합니다. 이 짧은 제목·해설 작업에서는 `reasoning.effort: none`을 사용합니다. 최신·최저가 모델이라고 가정하지 않습니다.
- 호출: FastAPI의 `backend/curator.py`에서 Python 표준 HTTP 클라이언트로 고정 주소 `https://api.openai.com/v1/responses`에 POST. `text.format`의 strict JSON Schema로 `titles` 3개와 `description_sentences` 2~4개를 요구한 후 Pydantic으로 다시 검사합니다. 배열의 문장은 최종 설명 한 개로 조합합니다.
- 제목 길이 2~50자·한국어·개수·중복/매우 유사한 후보, 설명 언어·문장 형식·길이를 검증합니다. 원문에 없는 구체적 사실을 만들지 않도록 지시하고 사용자 확인을 요구합니다. 구조 검증이 사실 충실도나 문학적 품질을 보장하는 것은 아닙니다.
- 사용자 버튼에서만 호출, 생성 요청당 OpenAI POST 1회, 자동 재시도 없음. HTTP 리다이렉트도 따르지 않습니다. 출력 상한 1000토큰, `store: false`, 네트워크 timeout 기본 20초(설정 범위 5~25초), 브라우저 대기 상한 30초입니다.
- 단일 서버 프로세스 메모리 기준 10분 동안 방문객별 5회·연결 IP별 10회·프로세스 전체 30회, 동시 처리 최대 2건입니다. 같은 방문객 또는 IP의 동시 요청과 같은 방문객/요청 UUID 재전송은 409, 횟수/전체 동시 한도는 429입니다. 제공사로 보낸 실패 요청도 횟수에 포함합니다.
- 메모리 제한은 재시작 시 초기화되고 여러 worker/서버 사이에서 공유되지 않습니다. 데모 방문객 ID를 인증으로 신뢰하지 않으며 IP별·전체 제한을 함께 둡니다. 공개 서비스의 공유 제한/인증·운영 한도는 이후 별도 작업입니다.
- `OPENAI_API_KEY`, `OPENAI_CURATOR_MODEL`, `OPENAI_CURATOR_TIMEOUT_SECONDS`는 백엔드 프로세스 환경변수만 사용합니다. `backend/.env.example`에는 빈 키와 설정 예시만 있습니다. 예시 파일을 자동 로드하지 않으며 README의 마스킹 입력 예시로 설정할 수 있습니다. 키를 새로 발급하거나 사용자 키를 출력·코드·브라우저·로그·Git에 넣지 않았습니다.
- 키 없음 503, 제공사/연결 오류 503, 시간 초과 504, 거절·중단·잘못된 형식 502를 안전한 문구로 반환합니다. 원본 제공사 오류·키·요청 본문을 반환/로그하지 않습니다. 누락된 키 때문에 서버 시작이나 일반 작품 등록·조회가 실패하지 않습니다.
- 공식 문서 확인: [모델](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [운영·API 키](https://developers.openai.com/api/docs/guides/production-best-practices). 확인일 2026-11-02.

### SQLite와 호환성

- 이미 존재하는 선택 컬럼 `refined_description`을 사용하므로 새 테이블/컬럼이나 DB 초기화가 필요하지 않습니다. 이전 스키마에 컬럼이 없으면 기존 `database.initialize()`의 비파괴 컬럼 추가 경로가 적용됩니다.

`PLAN`/`SPEC`은 사진 MVP 이후 Phase 9에서 AI 이미지를 다루도록 되어 있습니다. 최신 사용자 요청에 따라 **AI 회화 생성·상설 전시관 통합에 필요한 부분만 먼저 구현**했습니다. Phase 3~8 또는 Phase 9 전체 완료로 간주하지 않으며 기획 문서를 크게 고치지 않았습니다. 사진 저장/변환·이미지 편집·삭제·투표·별도 AI 전시관 주소는 추가하지 않았습니다.

### 구현

- `/submit`: 기존 입력·선택 UI·큐레이터를 유지. 화풍 5종 선택 → 사용자 버튼에 의한 유료 생성 → 로딩/오류 → 미리보기 → 명시적 이미지 확인 → 기증 흐름을 추가했습니다. 큐레이터와 이미지는 독립 버튼으로만 호출합니다.
- 제목·원문·카테고리·확인된 설명·화풍이 생성 당시와 다르거나 24시간이 지났으면 이전 결과 기증을 막습니다. 설명이 있다면 확인 후 이미지에 반영하며 원문은 별도 보존합니다. 실패·시간 초과 시 입력을 유지하고 텍스트 모드로 기증할 수 있습니다.
- FastAPI `POST /api/image-generations`: `gpt-image-2`, `medium`, `1024x1024`, PNG 1장 고정. 서버에서 기존 `OPENAI_API_KEY`만 읽고 Images API를 직접 호출합니다. 브라우저는 모델·장수·품질·경로를 지정하지 못합니다. 기존 큐레이터 모델/API 설정을 변경하지 않았습니다.
- 프롬프트: 작품명·원문·확인 설명을 자료로 제공하고 수채화/유화/점묘/흑연/콜라주의 재료 질감·빛·구성·상징·회화적 표현을 강조합니다. 글자·제목·서명·워터마크·특정 생존 작가 모방을 피하도록 지시합니다. 실제 준수·품질은 미검증입니다.
- 기존 상세 액자의 `object-fit: contain`을 유지하고 새 API 이미지 주소를 백엔드 origin으로 해석합니다. 갤러리도 기증 이미지가 있으면 비율을 유지해 표시하며 실패하면 원문 카드로 돌아갑니다. 기존 이미지 없는 작품은 placeholder/설명으로 유지됩니다. 조회는 생성 API를 호출하지 않습니다.

### 비용·접근 권한

2026-11-02 공식 문서 기준 GPT Image 2의 1024² 예상 출력은 low $0.006 / medium $0.053 / high $0.211이고 입력 프롬프트 비용은 별도입니다. 최신 GPT Image 2.5 Flare/Sunburst도 검토했으며 출력 $30/100만 토큰, low~max 옵션입니다. GPT Image 1.5는 Deprecated 표시라 선택하지 않았습니다. 현재 지원 API와 크기별 출력 비용을 확인할 수 있는 GPT Image 2를 선택하고 앱은 medium 정사각 한 장으로 고정했습니다. [공식 생성 가이드](https://developers.openai.com/api/docs/guides/image-generation), [API](https://developers.openai.com/api/reference/resources/images/methods/generate).

- 기본 `OPENAI_IMAGE_ENABLED=0`. 기존 키·환경 파일을 변경하지 않았습니다. 작업 터미널에는 키가 없어 인증된 모델 목록 확인은 불가능했으며 공유 프로젝트의 생성 권한·조직 인증·결제 상태는 미검증입니다. 실제 생성 API를 권한 확인용으로 호출하지 않았습니다.
- SQLite 예약 원장에 호출 전 기록. 기본 24시간 3회·누적 10회·누적 예약액 $1, 시도당 $0.10 예약. 방문객 또는 연결 IP 5분 간격, 전체 진행 중 1건. 동일 요청 UUID 중복 거절. 실패/시간 초과도 누적하며 재시작·미리보기 파일 정리로 초기화되지 않습니다.
- 서버 네트워크 120초·브라우저 대기 150초. 자동 재시도·리다이렉트 재전송·자동 재생성 없음. 원문·키·제공사 오류 본문을 로그/응답에 내보내지 않습니다.
- 예약액은 실제 청구액/계정 강제 상한이 아닙니다. 공유 키의 다른 앱 사용량도 제한하지 못합니다. 첫 유료 테스트는 README의 1회·10센트 예약 설정과 선생님이 허용한 사용량을 확인한 뒤 별도로 진행합니다. 한도가 소진되었다고 원장을 삭제하지 않습니다. 임시 방문객 ID는 실제 인증이 아닙니다.

### DB·파일 보존

- 기존 `artworks`의 선택 메타데이터 필드를 그대로 사용하며 원문·번호·날짜를 보존합니다. 새 `image_generations` 테이블만 추가하고 생성 시도/비공개 준비/해시 토큰/작품 연결/예약액을 기록합니다. 후보 제목이나 원본 PNG 바이트를 작품 테이블에 넣지 않습니다.
- `uploads/paintings/{서버 UUID}.png`는 Git 제외·비공개 디렉터리입니다. 외부 URL 다운로드나 임의 경로/사진 업로드를 받지 않습니다. PNG 컨테이너·치수·청크 체크섬을 확인한 뒤 임시 파일→flush/fsync→원자적 이름 변경→준비 기록 순으로 처리합니다.
- 생성 응답의 미리보기는 브라우저 메모리에만 표시합니다. 무작위 확인 토큰은 DB에 해시로 저장하며 URL·localStorage에 넣지 않습니다. 생성만 하고 떠난 결과는 공개 작품이 아닙니다.
- 기증 시 토큰·방문객·작품 내용·만료·파일 해시를 검사하고 DB 트랜잭션으로 작품/이미지를 함께 연결합니다. 파일 저장·준비 기록 실패는 새 파일을 정리하고, 기증 연결 실패는 작품 삽입을 함께 되돌립니다. 재시도는 같은 기증 요청으로 중복 저장을 막습니다.
- 공개 이미지 경로는 `GET /api/artworks/{id}/image`이며 기증된 결과만 반환합니다. 미등록/없는 이미지는 404, 파일 누락/손상은 503입니다. 만료된 비기증 파일과 강제 종료 잔여 tmp는 README의 로컬 유지보수로 정리할 수 있습니다. 기증 작품/파일과 비용 원장은 보존합니다.
- 이번 작업은 실제 DB를 마이그레이션하거나 기존 개발 서버를 재시작하지 않았습니다. 새 테이블은 사용자가 백엔드를 재시작할 때 안전하게 추가됩니다. 테스트는 임시 DB/폴더만 사용했고 실제 DB SHA-256이 작업 전후 동일했습니다.

### 방문객 ID의 보안 한계

**이 기능은 로컬 데모 수준의 소유자 구분이며 정식 인증·공개 서비스의 안전한 사용자 권한을 보장하지 않습니다.** localStorage의 방문객 ID를 복사·조작한 사람을 실제 기증자와 구별할 수 없습니다. 서버의 ID 비교는 다른 ID의 요청을 거절하지만, 기증자의 ID 자체가 도용된 경우를 막는 인증 수단이 아닙니다. 같은 작가명은 권한을 주지 않습니다. 다른 브라우저·기기·origin 또는 저장소 삭제 후에는 기존 작품의 소유자로 인식되지 않을 수 있으며 복구 기능은 없습니다.

### 삭제 이미지의 안전한 정리 정책

- 삭제 요청에서는 **실제 이미지 파일을 직접 삭제하지 않습니다.** 생성 이미지 원장의 `artwork_id`를 비우고 상태를 `expired`로 바꾼 뒤 작품을 삭제합니다. 오류가 나면 이 DB 변경을 모두 되돌립니다.
- 삭제 성공 후 서버의 해당 상세·이미지 API는 404이고 목록에서 작품이 빠집니다. 같은 이미지 확인 토큰도 다시 기증할 수 없습니다. 비용 예약 원장·요청 중복 기록은 보존해 삭제로 비용 한도가 초기화되지 않습니다.
- PNG는 비공개 저장소에 남겨 안전하게 보존합니다. 이후 관리자가 백업·검토 후 README 14절의 기존 **명시적** `cleanup_previews()`를 실행하면 원래 만료 시각이 지난 비연결 파일을 정리할 수 있습니다. 이번 작업에서는 실제 저장소에 이 명령을 실행하지 않았고 자동 정리 기능도 추가하지 않았습니다.
- 사진/외부 이미지 URL로부터 경로를 추측해 삭제하지 않습니다. 다른 작품의 파일은 건드리지 않습니다. 이미 다운로드된 사본이나 과거 캐시까지 회수한다고 보장하지 않습니다.
- DB 테이블·컬럼 추가나 실제 데이터 마이그레이션은 없습니다. 미래 투표 테이블의 연결 삭제는 Phase 4에서 구현·검증합니다.

### AI 설명 누락 현상: 원인 미확정

- 사용자가 한때 생성 설명이 기증 후 상세·수정 화면에 없다고 보고했고, 기증 직전 확인란은 선택되어 있었다고 답했습니다. 이후 브라우저에서 설명이 다시 정상 표시된다는 보고가 있었습니다. **누락 원인을 확정하거나 오류 수정 완료로 기록하지 않습니다.**
- 실제 DB와 GET을 읽기 전용으로 대조했을 때 설명이 NULL인 작품과 저장된 설명이 있는 작품이 함께 존재했습니다. 저장된 설명은 DB·목록·상세 응답이 일치했고 반복 GET에서도 동일했습니다. 정상 표시 보고를 NULL 작품의 자동 복구로 해석하지 않습니다.
- 상세 표시 함수·수정 폼 초기값·수정 요청 본문 생성은 저장된 설명을 유지합니다. 모의 AI 응답과 임시 DB에서 확인된 설명 등록 → SQLite/GET → 수정 화면 전달 → 제목만 수정 → 설명 수정 → 재시작 유지 및 설명 없는 텍스트 작품을 회귀 검사했습니다.
- 확인 상태가 해제되면 등록 요청에서 설명을 생략하는 코드 경로는 있지만, 사용자의 확인 상태 보고와 실패 당시 요청 본문을 대조하지 못해 이번 원인으로 단정하지 않았습니다. 원문·설명을 분리하고 사용자가 확인한 설명만 저장하는 정책은 유지합니다.
- 원인이 불명확해 제품 코드를 추측으로 변경하거나 실제 작품의 NULL 설명을 채우지 않았습니다. 이미 누락된 원문은 당시 응답·복사본 등이 있어야 정확한 복구를 검토할 수 있습니다. 재발 시 새 유료 요청 대신 기존 `POST /api/artworks`의 Payload/Response에서 설명 필드·확인 상태·작품 번호를 먼저 확인해야 합니다.

### API와 저장 구조

| API | 동작 |
| --- | --- |
| `PUT /api/artworks/{id}/recognition` | 본문 `visitor_id` UUID4의 명작 인정 추가. 이미 인정했다면 중복 행 없이 현재 상태 반환 |
| `DELETE /api/artworks/{id}/recognition` | 같은 본문의 방문객 인정 취소. 표가 없어도 현재 상태 반환. 작품 삭제 API와 별개 |
| `GET /api/artworks/{id}` | 기존 상세 정보에 `recognition_count`, `recognized_by_me` 추가. 개인 상태는 기존 `X-Visitor-ID` 헤더로 조회 |
| `GET /api/artworks?order=latest\|popular&category=…` | 최신순 기본값 유지. 선택한 정렬·다섯 카테고리 필터 함께 적용. 공개 인정 수 포함 |
| `GET /api/hall-of-fame` | 실제 작품 TOP 10. 인정 수 내림차순 → 기증일 오름차순 → ID 오름차순 |

- 투표 응답은 `artwork_id`, `recognition_count`, `recognized_by_me`입니다. 없는 작품 404, 잘못된 ID/본문 422, DB 실패 503으로 기존 오류 처리와 연결했습니다. 개인 상태 응답은 기존 방문객 ID 자체를 노출하지 않습니다.
- `artwork_recognitions(artwork_id, visitor_id, created_at)`를 서버 시작 시 추가합니다. 복합 기본키 `(artwork_id, visitor_id)`로 중복을 막고 외래키 `ON DELETE CASCADE` 및 연결별 `foreign_keys=ON`으로 작품 삭제 시 해당 표를 같은 트랜잭션에서 정리합니다.
- `BEGIN IMMEDIATE` 트랜잭션으로 작품 존재 확인·추가/취소·결과 조회를 묶었습니다. 별도 증가 카운터 없이 실제 투표 행에서 인정 수를 계산해 중복 증가·음수 카운트를 피합니다. 작품 수정은 표를 건드리지 않습니다.
- 기존 작품 테이블·데이터를 초기화하지 않습니다. 실제 DB에 새 테이블을 만들기 위한 서버 재시작은 이번 자동 검사에서 수행하지 않았으며, 임시 DB에서 추가 마이그레이션을 검증했습니다. 기존 작품 이미지 정리 정책과 AI 설명·이미지 연결 구조는 그대로입니다.

- 상세의 기존 작품 설명 영역에 실제 인정 수·현재 방문객의 눌림 상태·인정/취소 버튼을 추가했습니다. 요청 중 버튼과 ref 잠금으로 연속 클릭을 막습니다. 방문객 ID를 사용할 수 없거나 도중 바뀌면 투표를 제한합니다.

새 테스트의 기대값을 검토할 때, 수정된 작품에 오래된 기증 요청을 재전송하면 기존 409 충돌 보호가 정상 작동함을 확인했습니다. 제품 보호 동작을 바꾸지 않고 수정 전 멱등 재전송 성공/수정 후 충돌 거절로 검사했습니다. 최종 검사에 실패·스킵 항목은 없습니다.

작업 전후 실제 SQLite 파일 해시가 동일하며 기존 업로드 이미지 삭제/초기화를 수행하지 않았습니다. 히어로·공통 액자·전체 CSS·큐레이터/회화 구현·기존 미추적 에셋 해시도 동일했습니다. 이미지 생성 환경 설정을 변경하지 않았고 기본 `OPENAI_IMAGE_ENABLED=0`을 유지했습니다. 자동 검사는 실제 키를 비운 자식 프로세스와 모의 전송에서만 실행했으며 유료 OpenAI 호출·패키지 설치는 없었습니다. 기존 AI 설명 누락 현상의 원인은 여전히 미확정입니다.

### 직접 확인할 순서와 남은 작업

1. 이미지 생성을 OFF로 둔 상태로 백엔드와 프론트엔드 개발 서버를 재시작해 새 API와 추가 테이블을 반영합니다. DB 초기화 명령을 실행하지 않습니다.
2. 같은 주소/브라우저에서 테스트용 작품 상세를 열어 인정 → 취소, 빠른 연속 클릭, 새로고침 후 개인 상태와 수를 확인합니다. 서버 재시작 뒤에도 유지되는지 확인합니다.
3. 다른 브라우저/시크릿 창으로 같은 작품에 참여해 독립 투표와 전체 수를 확인합니다. 현재 데모 정책상 본인 작품도 허용합니다.
4. `/gallery`에서 다섯 카테고리와 인기순을 함께 선택하고, `/hall-of-fame`에서 실제 순서·상세 이동·TOP 3·이미지/텍스트·작품 수가 적은 경우를 확인합니다. 빈/오류 검사는 실제 DB를 비우는 대신 별도 테스트 환경에서 진행합니다.
5. 테스트용 작품만 수정해 표 유지, 삭제해 표/순위 제외를 확인하고 네트워크 오류 안내와 모바일 배치를 점검합니다. 기존 사용자 작품이나 유료 생성으로 검사하지 않습니다.
6. 브라우저 확인 및 별도 요청에 따른 Git 저장이 남아 있습니다. 이번 변경은 **미커밋**입니다. 다음 Phase 5는 랜덤 작품 감상과 이용 흐름 개선이며 이번에는 구현하지 않았습니다.
